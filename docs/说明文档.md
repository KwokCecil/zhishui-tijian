# 智税体检 Agent 架构分析

> 四个文件：`llm.py`、`tools.py`、`agent.py`、`app.py`  
> 核心思想：规则引擎负责判断，大模型负责调度和表达。

---

## 0. 总览

这不是“让大模型直接算税”的 Agent，而是一个“规则引擎负责判断，大模型负责调度和表达”的受控 Agent。

四个文件分别像四层：

- `llm.py`：嘴和耳朵，负责和模型 API 说话。
- `tools.py`：手和脚，把规则、政策、评分、演示数据包装成模型能调用的工具。
- `agent.py`：大脑和纪律委员，决定怎么调工具、怎么防幻觉、怎么组织回答。
- `app.py`：脸和操作台，Streamlit 页面，给用户看结果、上传数据、聊天、生成报告。

依赖关系：

```text
用户
  ↓
app.py 页面
  ↓
agent.py 对话总控
  ↓              ↓
llm.py 调模型    tools.py 调工具
                 ↓
        rules / policies / scoring / generate_data
```

页面上的风险指数、命中规则、政策匹配，主要是规则引擎算出来的，不是模型编出来的。

## 1. llm.py：模型通信层

### 1.1 它是什么

`llm.py` 是一个极简的 OpenAI 兼容客户端。它不关心税务逻辑，只负责：

- 读取模型配置；
- 判断有没有配置 API Key；
- 发单轮请求；
- 发多轮 function calling 请求；
- 把模型要调用的工具转交给 `tools.py` 执行。

可以把它理解成“电话线”和“翻译器”。

### 1.2 组成和功能

#### `config()`

读取三个环境变量：

- `ZHI_SHUI_LLM_API_KEY`
- `ZHI_SHUI_LLM_BASE_URL`
- `ZHI_SHUI_LLM_MODEL`

默认 base URL 是 DeepSeek，默认模型是 `deepseek-flash`（DeepSeek 现行命名；旧名 `deepseek-chat`／`deepseek-v4-flash` 由服务端映射到同一模型）。  
兼容 OpenAI 风格接口，不绑定某一家模型。

#### `available()`

判断是否真的配置了 API Key。  
如果 Key 是空的、包含“在这里填入”、包含“your_key”，就认为不可用。  
页面可以自动决定：走在线模型，还是走离线演示。

#### `complete()`

单轮补全。主要给“生成报告”用。  
把 system prompt 和 user prompt 发给模型，拿回一段文本。  
不做工具调用，就是普通聊天补全。

#### `chat_with_tools()`

最核心的函数：多轮 function calling 循环。

流程：

1. 把 messages、tools 发给模型；
2. 模型可能返回 `tool_calls`，说“我要调用某个工具”；
3. 程序执行工具；
4. 把工具结果作为 `role: tool` 消息回填给模型；
5. 模型继续判断，直到给出最终回答，或者调用 `stop_tool`。

重要细节：

- `max_turns=8`：最多循环 8 轮，防止模型无限调工具。
- `executed` 缓存：同一个工具、同一组参数，如果已经调用过，就不重复执行，只返回“已调用过，结果不变”。
- `stop_tool`：如果模型调用的是 `submit_answer`，立即结束循环，并返回 `submitted` 结构化结果。这样模型没有机会在自由文本尾部写“需要我继续吗”这种客套话。
- 轮数用尽后，会强制再发一次请求，`tool_choice: "none"`，告诉模型“不要再调工具，直接根据已有结果回答”。
- `_run_tool()` 延迟导入 `tools.execute_tool`，避免循环依赖。

### 1.3 为什么这样设计

因为大模型本身不可靠，不能让它直接查数据库、直接算税、直接编政策。  
所以 `llm.py` 只做“通信”，真正的判断交给工具层。  
这样模型换供应商也没关系，只要兼容 OpenAI 接口即可。

## 2. tools.py：工具层 / 能力层

### 2.1 它是什么

`tools.py` 是 Agent 的“工具箱”。  
它把规则引擎、政策库、评分、演示数据、报告生成，全部包装成标准工具。  
每个工具长这样：

```python
{
  "name": 工具名,
  "description": 工具说明,
  "parameters": JSON Schema 参数,
  "required": 必填参数,
  "execute": 真正执行的函数
}
```

大模型看到的不是 Python 函数，而是 `tool_schemas()` 生成的 OpenAI function calling schema。  
模型只能按 JSON 参数调用，不能直接改代码。

### 2.2 主要工具

#### `load_scenario`

加载内置演示场景，比如 `clean`、`risk`、`fuel`、`solar`、`lotus`。  
把数据注册到 `DATA_CONTEXT`，返回企业概况和行数摘要。  
之后体检时只要传 `scenario=场景名`，不用把完整数据复制给模型。

#### `get_demo_scenario`

获取完整演示数据 JSON。  
和 `load_scenario` 类似，但返回更完整的数据。

#### `run_tax_health_check`

核心体检工具。  
接收企业指标、发票、资金流水、合同、外部单据、数据源，或者直接传 `scenario`。  
内部调用 `rules.run_all()` 跑规则，再调用 `scoring.risk_summary()` 算风险指数。  
返回：

- `summary`：风险指数、等级、命中数、Top3 等；
- `hits`：命中的规则明细。

关键设计：  
如果传了 `scenario`，优先从 `DATA_CONTEXT` 取数据；取不到才用 `generate_data.build_scenario()`。  
上传场景用 `scenario="upload"`。  
工具描述里明确说“不要手工复制完整数据”，这是为了省 token、防止模型抄错。

#### `match_policy_cards`

按企业指标匹配政策卡片。  
返回可享受、需人工确认、不适用等状态，每条带文号。  
只处理已收录政策，超范围不猜。

#### `check_small_micro`

逐项判断小型微利企业条件：

- 从业人数 ≤ 300；
- 资产总额 ≤ 5000 万；
- 应纳税所得额 ≤ 300 万；
- 非限制禁止行业。

返回每项是否通过和当前数值。

#### `answer_policy_question`

处理未收录政策问答。  
本 Demo 只支持已收录政策卡片，超范围统一拒绝并引导 12366。  
防止模型瞎编政策。

#### `generate_report`

把 `hits`、`summary`、`matched` 翻译成 Markdown 报告。  
调用 `llm.complete()`，如果失败，就用 `_default_report()` 离线模板。  
只做表达和排版，不新增判断。

#### `submit_answer`

对话回答的“结构化提交工具”。  
模型不直接用自由文本回答，而是调用它提交：

- `conclusion`：一句话结论；
- `facts`：事实发现，每条以规则编号开头；
- `actions`：企业自查动作；
- `need_info`：需要用户补充的数据。

为什么这样？  
因为自由文本容易跑偏、写客套话、重复、编证据。  
结构化提交后，`agent.py` 可以按规则库重建事实，模型只给编号，不能编证据。

### 2.3 辅助函数和机制

- `_profile_df`、`_invoices_df` 等：把 JSON 转成 DataFrame，并保证列顺序和 `generate_data` 一致。
- `TOOLS`：全局工具注册表。
- `DATA_CONTEXT`：场景数据句柄，避免把大表塞进 prompt。
- `set_data`：注册数据。
- `tool` 装饰器：把函数注册成工具。
- `tool_schemas()`：生成 OpenAI function calling schema。
- `execute_tool()`：按名字执行工具。
- `_parse_arguments()`：容错解析模型生成的 JSON 参数，比如剥代码围栏、截取大括号、清尾逗号。

### 2.4 为什么这样设计

一句话：让模型“能调用能力”，但不能“篡改能力”。  
税务判断必须可审计、可复现，所以规则写在工具里，模型只负责选择工具和表达结果。

## 3. agent.py：Agent 编排与约束层

### 3.1 它是什么

`agent.py` 是对话总控。  
它决定：

- 用户问题是不是离题；
- 是不是要生成报告；
- 走在线大模型模式，还是离线关键词模式；
- 怎么把模型、工具、历史、结构化回答串起来；
- 怎么清洗和兜底，防止模型乱说。

它是“大脑 + 纪律委员”。

### 3.2 系统提示词

`SYSTEM_PROMPT` 有 19 条规则，核心是：

- 判断必须来自工具事实；
- 回答带溯源；
- 超范围政策不猜，引导 12366；
- 数据是演示模拟；
- 先调工具再回答；
- 回答简短；
- 不重复调用工具；
- 内置场景先加载再体检；
- 不说工具名；
- 不用 Markdown；
- 对话必须通过 `submit_answer` 提交；
- 多轮不重复；
- 追问按需裁剪；
- 不写服务性引导；
- 不做法律后果定性。

这些规则会直接影响模型行为。

### 3.3 关键流程

#### `run_agent()`

总入口：

1. 如果离题，直接拒绝；
2. 如果用户要报告，走 `_build_report()`；
3. 如果模型可用，走 `_run_llm_agent()`；
4. 否则走 `_run_offline_agent()`。

#### `_build_report()`

用户说“生成报告”“下载报告”时，不走自由对话。  
直接调用工具：

- 加载数据；
- 跑体检；
- 匹配政策；
- 生成报告。

报告生成路径是确定性的，不让模型自由发挥。

#### `_run_llm_agent()`

在线模式核心：

1. 如果是上传数据，注册到 `upload` 句柄；
2. 准备上下文提示，告诉模型当前场景和应该怎么调；
3. 取最近 4 条历史，截断 800 字符，防止上下文太长；
4. 把 system prompt、历史、当前问题发给 `llm.chat_with_tools()`；
5. 拿到 `answer`、`trace`、`submitted`；
6. 检查是否有真实工具成功执行；
7. 如果 `submitted` 有效，调用 `_render_submitted()` 渲染；
8. 如果没有有效体检结果，降级到离线模式；
9. 如果清洗后为空，也降级。

关键点：  
`tool_ok` 要求至少有一个非 `submit_answer` 的工具成功。  
模型不能只提交一个结论，必须有真实工具结果支撑。

#### `_render_submitted()`

把结构化提交渲染成回答：

- 结论；
- 事实发现；
- 下一步；
- 需要你补充。

事实部分由 `_build_fact()` 处理：

- 如果以 `Rxxx` 或 `Gxxx` 开头，就去规则库 `hits_by_id` 里查；
- 查到就用规则库的 `name`、`level`、`evidence` 重建；
- 查不到就丢弃，防止编造；
- 如果上一轮已经说过这个规则编号，也丢弃，防止重复；
- 无编号的事实保留，比如政策条件。

关键：模型只给编号，证据由系统填。模型写不出假证据。

#### `_clean_answer()`

兜底清洗：

- 把工具名替换成自然语言；
- 去掉 Markdown 标记；
- 压缩空行；
- 删除尾部服务性引导，比如“如需继续，我可以帮你整理”。

`_strip_service_tail()` 只做减法，不注入替代文案，最多删 2 句，而且不会把非空回答清空。

#### `_run_offline_agent()`

离线模式用关键词路由：

- 问“优惠/政策/享受/减免” → 调 `match_policy_cards`；
- 问“小微/小型微利” → 调 `check_small_micro`；
- 问“风险/体检/问题/检查/健康/怎么样/安全” → 调 `run_tax_health_check`；
- 问“行动/建议/下一步/整改/怎么办/处理/措施” → 调体检并给优先级建议；
- 都不匹配 → 给引导。

不依赖网络，用于演示“意图 → 工具 → 事实 → 回答”的完整链路。

### 3.4 为什么这样设计

因为大模型容易：

- 编政策；
- 编金额；
- 编规则；
- 重复；
- 写客套话；
- 跑题；
- 做法律定性。

所以 `agent.py` 用多层机制约束它：

- 系统提示词；
- 工具结果校验；
- 结构化提交；
- 规则库重建事实；
- 多轮去重；
- 文本清洗；
- 在线失败降级离线。

## 4. app.py：前端与交互层

### 4.1 它是什么

`app.py` 是 Streamlit 页面，是用户直接看到和操作的地方。  
不只是聊天窗口，还包括：

- 数据源选择；
- 场景说明；
- CSV 上传；
- 规则体检结果展示；
- 政策机会；
- 行动建议；
- 风险指数解释；
- AI 报告生成；
- Agent 对话；
- 纯大模型 vs 规则+大模型对比演示。

### 4.2 主要组成

#### 页面配置和样式

设置标题、图标、宽布局。  
注入 CSS，做指标卡、标签、气泡、场景框等样式。  
从 `st.secrets` 读取 API Key 等环境变量。

#### 侧边栏数据源

两种模式：

- 内置演示场景；
- 上传 CSV。

内置场景：

- `clean`：对照组，低风险；
- `risk`：软件企业混合风险；
- `fuel`：加油站三源比对；
- `solar`：光伏设备小微临界；
- `lotus`：莲子加工收购凭证。

上传模式支持下载 CSV 模板，上传企业指标、发票、资金流水、合同、外部单据、数据源。  
然后调用 `contract.validate_tables()` 做数据契约校验。

#### 主区体检展示

页面直接调用：

- `rules.run_all()` 跑规则；
- `scoring.risk_summary()` 算风险；
- `policies.match_cards()` 匹配政策。

展示：

- 体检对象摘要；
- 命中风险提示；
- 风险指数、等级、命中特征数、可关注政策数；
- 命中特征：组合规则和独立规则分开；
- 优惠政策：可享受、需人工确认、命中限制、不适用；
- 行动建议：按高、中、低分组；
- 指数怎么算：高 60、中 30、低 10，≥60 高风险，30-59 中风险，<30 低风险；
- AI 体检报告：按钮生成，可下载 Markdown，可预览。

#### Agent 对话

对话区使用 `st.session_state` 保存历史。  
用户输入后，先把用户消息加入历史，设置 `pending_prompt`，然后 `st.rerun()`。  
下一轮再真正调用 `_ask_agent()`，显示“Agent 正在调用工具…”。  
返回后把 assistant 回答加入历史，保存 `last_trace`、`last_mode`，再 rerun。

`_ask_agent()` 是统一入口：

- 内置场景传 `scenario`；
- 上传场景传 `profile`、`invoices`、`fund_flows`、`contracts` 等；
- 如果在线失败，自动降级到 `agent._run_offline_agent()`。

工具调用轨迹放在 expander 里，用户可以看到调了哪些工具、返回什么。  
这是可解释性的体现。

#### 对比演示

同一个问题、同一份数据，做两路：

- 左路：纯大模型直接看前 30 行数据，直接回答，容易幻觉；
- 右路：本产品路径，规则引擎出事实，模型只表达。

用来展示“为什么不能只靠大模型”。

### 4.3 为什么这样设计

因为用户需要：

- 看到确定性体检结果；
- 能上传自己的数据；
- 能问问题；
- 能下载报告；
- 能看到工具调用轨迹；
- 能理解风险指数怎么来的；
- 能对比纯模型和规则+模型。

`app.py` 把规则引擎的确定性结果和大模型的交互能力结合起来。

## 5. 一次完整对话怎么走

以在线模式为例：

1. 用户在 `app.py` 输入：“这家公司有什么风险？”
2. `app.py` 把用户消息存入 `chat_history`，设置 `pending_prompt`，刷新页面。
3. 下一轮 `app.py` 取出 `pending_prompt`，调用 `agent.run_agent()`。
4. `agent.run_agent()` 判断不是离题，不是报告意图，模型可用，走 `_run_llm_agent()`。
5. `_run_llm_agent()` 准备上下文，告诉模型当前场景。
6. 调用 `llm.chat_with_tools()`。
7. 模型决定调用 `run_tax_health_check`。
8. `llm.py` 把工具调用转给 `tools.execute_tool()`。
9. `tools.py` 调用 `rules.run_all()` 和 `scoring.risk_summary()`，返回 `summary` 和 `hits`。
10. 工具结果回填给模型。
11. 模型调用 `submit_answer` 提交结构化回答。
12. `llm.chat_with_tools()` 遇到 `stop_tool`，立即结束，返回 `submitted`。
13. `agent._render_submitted()` 用规则库重建事实，生成最终回答。
14. `app.py` 把回答加入聊天历史，保存工具轨迹，展示给用户。

离线模式类似，只是第 6 步不是模型决定工具，而是关键词路由决定工具。

## 6. 为什么整体要这么设计

核心设计原则有 8 条：

1. **判断与表达分离**  
   规则引擎判断，模型表达。模型不能改判断。

2. **工具化**  
   所有能力都包装成标准工具，模型只能调用，不能篡改。

3. **数据句柄化**  
   内置场景先 `load_scenario`，之后只传 `scenario`，不把大表复制进 prompt。省 token，也防抄错。

4. **结构化提交**  
   模型通过 `submit_answer` 提交结论、事实编号、动作、需要补充的信息。  
   事实证据由系统按规则库填充，模型编不了。

5. **多层兜底**  
   在线失败降级离线；报告失败用离线模板；回答清洗；工具名替换；服务性尾巴删除。

6. **可审计**  
   `trace` 记录每次工具调用和结果，页面可展开查看。

7. **多轮体验**  
   历史只取最近 4 条，截断 800 字符；上一轮说过的规则编号本轮不再重复。

8. **安全合规**  
   不做法律后果定性，不出现“刑事”“犯罪”“罚款倍数”等表述。  
   超范围政策引导 12366，不猜。

## 7. 小白记忆版

- `llm.py`：电话线，负责和模型说话。
- `tools.py`：工具箱，里面是体检、政策、小微、报告、提交答案等工具。
- `agent.py`：总控护士，规定模型只能按流程走，不能乱说，最后整理成标准回答。
- `app.py`：医院大厅和仪表盘，用户在这里选数据、看报告、聊天、对比。

整个 Agent 的本质：

> 大模型不是税务专家，它只是调度员和表达员。  
> 真正的税务专家是规则引擎。  
> 大模型负责决定“查什么、怎么说”，规则引擎负责“是什么、为什么、风险多大”。  
> 这样既能用大模型的自然语言能力，又能保证税务判断可溯源、可复现、不幻觉。
